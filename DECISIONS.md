# Decisions

Ambiguities resolved during implementation. Format: date — question → choice (why).

- 2026-11-16 — **npm scripts on a path with `&`.** The repository folder name contains `&`, which breaks npm's Windows `.cmd` shims (`npx`, `node_modules/.bin`). → All scripts call tool entry points directly (`node ../../node_modules/typescript/bin/tsc`, etc.). Works identically on Linux/macOS. (Renaming the folder would also fix it, but that is the user's call.)
- 2026-11-16 — **What does "build" mean for source-only packages?** `core` and `fixtures` are consumed as TypeScript source by Vite/Vitest. → `core` build emits `dist/` with declarations (useful for the Batch 2 server); `fixtures` build is a strict no-emit compile of `src`. (Keeps one tsconfig per package; no project-reference plumbing.)
- 2026-11-16 — **Router.** `HashRouter` in the prototype so the static build works from any folder or static host without rewrite rules.

## M1 — domain core

- 2026-11-16 — **When is an OR choice "open"?** The concept says the editor preselects the first option with enough stock *and* that confirmation is blocked while an OR choice is open. → An OR group is **open only when no person chose and no option is available**; then the first option is shown provisionally and confirmation is blocked until someone picks. A preselected (available) option counts as decided. A person's choice is stored per booking (`orChoices`) and always wins; a previous preselection is kept while it stays available. (Avoids forcing a click on every OR group while still never confirming an unavailable mount.)
- 2026-11-16 — **Who is short when two confirmed orders collide?** → Orders have a confirmation sequence (`confirmSeq`); a confirmed order is evaluated only against orders confirmed **before** it. The later (overriding) order carries the conflict; the earlier one is not flagged. Drafts and pre-bookings are evaluated against all orders. (One conflict record per collision instead of two.)
- 2026-11-16 — **Conflicts that appear after confirmation** (service case opened, an order edited) → `recomputeConflictRecords` creates a `detected` conflict record (status *Nový*) on confirmed/packing orders that became short, notifying the Chief and PMs. Records resolve automatically when availability covers the line again.
- 2026-11-16 — **Lines without a source warehouse** → served from the booking's `defaultWarehouseId` if it stocks the item/case, else from the first warehouse that does. Splitting a line across warehouses is an explicit editor action (`splitLine`).
- 2026-11-16 — **External rental of a case-type shortage** → becomes an external line of the case type's primary item (first standard content) × pieces per case, e.g. "8× Astera AX9" for one AX9 case, matching the concept's Gala scenario. Accessories are assumed to come with the rented gear.
- 2026-11-16 — **One auto line per target.** Auto lines have stable ids `auto:item:<id>` / `auto:case:<id>` and sum all parents; once-per-order contributions take the max. A manual line of the same item stays a separate line.
- 2026-11-16 — **Line status Missing / Substituted** → such lines are inactive: they do not hold stock, are not packed and do not block confirmation.
- 2026-11-16 — **Missing pieces in vratka** → an `Issue` (type `missing`) is created as soon as a confirmed return line is short, and updated/archived by later sessions. Open missing issues hold stock (from the booking start, with no end) until resolved, which implements "returned with issues holds only the missing pieces, until resolved".
- 2026-11-16 — **Returned vs. closed** → a booking with every line settled goes to `returned` (stock free); `close` is an explicit Chief/warehouse action that makes it read-only. With open missing issues it is `returned_with_issues` and becomes `returned` when the last issue is resolved.
- 2026-11-16 — **Case lines in vratka** are confirmed one case at a time (one return entry per case number). A whole case not returned is a `missing` issue that holds the case and its contents. Event-to-event transfers are supported for loose-item lines only in Batch 1.
- 2026-11-16 — **Damaged pieces** → loose damaged pieces are not put back into a case (the case stays incomplete → refill task). A damaged piece counted inside a returned case stays in the case, and the service case references the case, so the case is not complete until the service case closes.
- 2026-11-16 — **Event-to-event transfer windows** → a line on B with `fromBookingId = A` is held from the day after A's last booked day (or from the actual handover day once it happens) until B ends. The handed-over pieces stop counting on A. No gap, no double count.
- 2026-11-16 — **Indicative price total** = Σ line day price × **event days** (not booked days with buffers). Case types are priced as the sum of their contents.
- 2026-11-16 — **Incomplete case reminders** (2 / 7 days) are skipped while the case or pieces taken from it are out on an active order; the clock restarts on the vratka day.
- 2026-11-16 — **Notification and thread texts** → core stores `type` + `params` and an English fallback `text`; the UI renders Czech from `cs.ts`. Keeps all Czech strings in one file.
- 2026-11-16 — **Lines added after shipping** → Chief only (the warehouse cannot create orders). The order goes back to `packing`; new lines and their auto accessories are flagged `addedAfterShipping`.

## M2 — fixtures

- 2026-11-16 — **How are fixture bookings built?** → Not as hand-written records: a small builder drives every booking through the real core API (create → lines → submit → confirm → pack → ship → vratka → close) with past dates up to "today" (2027-04-20). Shipments, return sessions, issues and conflict records are therefore always consistent with the rules; a fixture that would violate a rule fails the build.
- 2026-11-16 — **Connections count** → 144 instead of ~80: helper groups (power/DMX checks, shared desk OR group, hang-or-stand nested group) are expanded per fixture type. More coverage, same rule set.
- 2026-11-16 — **Scenario `galaDinner`** → the base data holds "Firemní den" (PM Jana Nováková, one AX9 case on 23–25 Apr). The Gala pre-booking itself is created by Petr during the demo (acceptance test 1); `GALA_STEPS` replays the full walk-through in tests. Brod has two AX9 cases and Karlák's AX9-03 starts incomplete, so the Gala is short exactly one case.
- 2026-11-16 — **"Affected order in May"** (concept step 9) → *Květnový festival* (PM Jana) books both Brod AX9 cases; the service case on AX9-02 makes it short and notifies its PM.
- 2026-11-16 — **Scenario `transfer`** → the base data already contains the planned TechConf → "Letní noc – warm-up" transfer (8 LEDBeams), so the scenario is the base state focused on those bookings.
- 2026-11-16 — **Scenario `caseBreaking`** → uses AX1, whose loose stock is zero (all 32 in four cases, one incomplete). With complete cases only, the plan's `broken` formula can never push `caseFree` below zero for a line that is green at item level, so the demo needs an incomplete case.
- 2026-11-16 — **Filler bookings** → 8 small PRNG bookings (seed 2027) avoid LEDBeams, AX1/AX9 and cases so the scenario numbers stay exact.
- 2026-11-16 — **Demo notifications** → notifications older than today are marked read; tonight's job (run for 2027-04-20) leaves fresh, unread reminders for the bell.

## M3 — prototype 1A

- 2026-11-16 — **Editor model** → the editor keeps a working copy of the booking and applies the core's pure edit functions (`addLine`, `setLineQty`, `chooseOr`, `coverWithExternal`, …) live; *Uložit / Odeslat / Potvrdit* store it through `saveBooking` and the lifecycle actions. Badges, conflicts, checks and recommendations are recomputed on every change.
- 2026-11-16 — **Override vs. external in the UI** → anyone who may confirm (Chief, PM with `canConfirmOwnOrders` on own booking) sees the override-reason field; only the Chief sees "Pokrýt externím pronájmem" and the Missing / Substituted markers, matching the concept's role table.
- 2026-11-16 — **Planned transfer source** → the line's source dropdown offers other orders that end within 14 days before this booking and contain the same item ("z akce …").
- 2026-11-16 — **Fonts** → IBM Plex Sans / Plex Sans Condensed bundled via `@fontsource` (no CDN at runtime).
- 2026-11-16 — **Screenshots** → `scripts/shot.mjs` (Playwright) captures pages of the running dev server for visual review; `PW_CHROME` may point at a local Chromium.

## M5 — independent prototypes

- 2026-11-16 — **Catalogue editing lives in core** (`catalog/edit.ts`): items, stock, connections, case types, cases, completeness and `importItems` are permission-checked core actions with tests, so Batch 2 can reuse them on the server. The UI only parses the sheet (SheetJS) into rows.
- 2026-11-16 — **Import matching** → rows update an existing item when the id or the exact name (case-insensitive) matches; otherwise they create one. Invalid rows are skipped and reported with row number and column; valid rows are applied (partial import), so a half-filled sheet is still useful.
- 2026-11-16 — **Stock cannot be set below the pieces inside cases** in that warehouse; adjust case contents first. Case contents cannot exceed warehouse stock.
- 2026-11-16 — **Completeness** = photo, home location, price > 0, at least one connection (in or out). "Potřebuje doplnit" lists items with fewer than 4/4.
- 2026-11-16 — **Packing**: the packer ticks lines and chooses specific case numbers (only complete cases not out on another order). For loose items the packer may name the case they were taken from; that case becomes incomplete. Ship quantity defaults to the remaining count and can be lowered (rest goes in a later batch).
- 2026-11-16 — **Vratka UI**: one card per line and one card per case; counts start at 0; "Kompletní dle standardu" fills one case only; there is no select-all. Damaged pieces in a case are counted against the case type's primary item (first standard content) in Batch 1.
- 2026-11-16 — **Service status flow** buttons follow the concept's order; "Odepsáno" is available from any open status. The responsible person, a Chief or anyone with `canManageService` may change status.

## Feedback after Batch 1

- 2026-11-16 — **Partly shipped orders disappeared from the packing list** (user feedback). → An order is `shipped` after its first batch (gear is out), but it now stays in the warehouse dashboard's packing list while `remainingToShip > 0`, marked "část odvezena, zbývá N ks". Ticking a case line on the packing screen now preselects the first free complete cases (previously shipping failed until case numbers were picked by hand).
- 2026-11-16 — **Category and subcategory system** (user request). → Two levels as in the concept (category → subcategory), now managed in the app: *Katalog → Kategorie* (Chief / catalogue editors) adds, renames, sets an icon and deletes categories. Rules in core (`upsertCategory`, `deleteCategory`): only two levels, names unique among siblings, only an empty category can be deleted (items are moved first via the table's bulk category change). Items may sit in a top category or a subcategory; a top category shows its subcategories' items too.
- 2026-11-16 — **Category view** → the *Karty* tab is a category browser: tree with counts, breadcrumb, subcategory chips; the selection is in the URL (`/catalog?cat=kab-opt`) so every category label ("Kabeláž › Optické kabely") links there. Labels appear on cards, item pages and the order editor's search results; the editor search also matches category names ("optické" finds all optical cables).
- 2026-11-16 — **Cable categories in the demo data** → Kabeláž: Napájecí kabely (PowerCON, IEC, CEE, prodlužky), Optické kabely (2 new items: Opticon 50 m, LC–LC 150 m), DMX, Audio, Síťové, Video kabely. Elektrodistribuce keeps distribution (rozvaděče, stmívače, rozbočky a adaptéry).
- 2026-11-16 — **Category colours** (user request: "tame"). → `Category.color` holds a key from a muted 10-colour UI palette (pale fill, soft border, readable text, stronger mark); subcategories inherit the parent's colour (`categoryColor`). Used on category labels, the tree, subcategory chips and a stripe on catalogue cards; chosen per category in *Katalog → Kategorie*. Deliberately muted so it never competes with the green/amber/red availability badges.
- 2026-11-16 — **"Balí se" until everything has left** (user request). → `shipBatch` keeps the order in `packing` while `remainingToShip > 0` and switches to `shipped` only when the last piece leaves; the UI shows "část odvezena, zbývá N ks" next to *Balí se*. Because part of the gear can already be at the event, vratka is allowed from `packing` once at least one batch has left (never before), and partly shipped orders also appear under *Očekávané vratky*. Consumables shipped during packing no longer double-count in holds.
- 2026-11-23 — **Public prototype on GitHub Pages** (user request; overrides the "everything runs locally" guardrail for static hosting only). → The repository is public and `.github/workflows/pages.yml` runs the quality gate and deploys `apps/proto/dist` on every push to `main`. Vite uses `base: './'`, so the build works from any sub-path (routing is already hash-based). Still no backend: each visitor's data stays in their own browser.
- 2026-11-23 — **Category on the booking's HW list** (user request). → Every line shows its category label. A case type has no category of its own, so it shows that of its primary item (first standard content); external lines have none. The label is not a link there, so a click cannot lose unsaved edits.
- 2026-11-23 — **"Používají ji" → "Je používán následujícími:"** (user request). → The subtitle "Co k tomu nutně potřebuješ" is dropped in that list, where it read backwards; it stays in "Propojení této položky". The other two subtitles are unchanged.
- 2026-11-23 — **Which orders can receive gear in a handover?** (user reported a finished order in the list) → `transferTargets` in core, used by the vratka list and by validation: other active orders, except those whose booked days ended before today *and* no later than the order being returned. An order that ended after it stays allowed, so a real handover can be recorded late.
- 2026-11-23 — **Dates in notifications** are stored as ISO days in the params and formatted in `cs.ts` ("26. 5. 2027").
- 2026-11-23 — **Pending issues explain themselves** (user feedback: "I don't know what is wrong there"). → Each entry on the Chief and warehouse dashboards says how many pieces came back, the vratka note, the event with dates and PM, who reported it and when, what stays blocked and what to do next; the resolve form says what each choice does to the stock. The same entry is shown on the booking's own page, so the PM sees it too. Only the Chief can resolve; the warehouse gets a link to the vratka.
- 2026-11-23 — **"Rozbije case" → "Rozdělí obsah casu"** (user request), also in the scenario name ("Rozdělení obsahu casu"). Code identifiers keep `breaksCase`.
- 2026-11-23 — **Scenario explanations** (user request) → a "?" next to *Scénář* opens on hover, focus or tap and says what each scenario shows and teaches. Native option tooltips are only a bonus: they differ between browsers and do not exist on phones.
- 2026-11-23 — **Notification importance** (user request) → three levels derived from the type in core (`notificationLevel`): *Naléhavé* (vibrant red), *Pozor* (amber), *Info* (tame grey); unread stand out, read ones fade, and the bell takes the colour of the most important unread one. Always with a text label, never colour alone. Not stored, so older saved data works too.
- 2026-11-25 — **Who adds and edits clients?** (user request; the concept only lists clients on the Admin screen) → PM, Chief and Admin add (`create_client`), PM and Chief right next to the client dropdown; Chief and Admin edit, archive and restore (`manage_clients`) on the new *Klienti* page. A PM cannot edit a client afterwards. No hard delete; a booking keeps an archived client, but none can newly pick it.
- 2026-11-25 — **Duplicate clients** → an identical active name (ignoring case and spacing) is refused, because two equal rows in a dropdown cannot be told apart; a similar one is only a warning with *Použít* (words of the shorter name begin words of the longer one, ignoring diacritics and legal form; typos are not caught). Merging duplicates is left until colleagues confirm they need it.
- 2026-11-25 — **Client contacts on the booking** → contact person, e-mail and phone are shown to everyone; the note only on *Klienti*, since it may hold deal terms. A client added on a booking page is stored at once, the booking's choice of client is stored with *Uložit*.
- 2026-11-25 — **Packing list as PDF** (user request; PDF export was outside Batch 1) → the packing screen has a paper version shown only in print; the browser print dialog offers "Save as PDF", so no PDF library or third-party service is needed. One section per warehouse (new page), cases as one block per physical case with its contents as tick boxes, signature lines. The document title becomes "Balicí list – <akce>" while printing, which is the suggested file name.
